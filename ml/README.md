# ML candidate filter — from-scratch setup guide

This folder trains a small model that helps the document-understanding engine decide which of
its detected "candidate" fields (captions, value boxes, table cells, checkboxes...) are real,
and which are noise. It does **not** detect fields itself — the Java engine already does that.
This model only learns to say "keep" or "discard" on candidates the engine already found.

If you're new to this project, read this whole file top to bottom before running anything —
each step depends on the one before it.

---

## 0. What you're actually building, in one picture

```
 source.pdf
     |
     v
 Java engine (deterministic — reads the PDF, finds every plausible field)
     |
     v
 debug.json  (hundreds of "candidate" fields, most of them wrong/duplicate/noise)
     |
     +---------------------------------------------+
     |                                               |
     v                                               v
 YOU review + correct  -->  expected.json      ml/extract_training_data.py
 (the ground truth: what                             |
  SHOULD have been found)                             v
     |                                          training_candidates.csv
     |                                          (one row per candidate,
     +--------------------------------------->   labeled real/noise by
        (used to grade every candidate)          comparing to expected.json)
                                                        |
                                                        v
                                                 ml/train_model.py
                                                        |
                                                        v
                                          a small model that learns to
                                          predict real vs. noise on its own
```

Your job, end to end, is: **add a PDF -> run the engine -> review its output by eye -> fix what's
wrong -> that becomes training data.** Nothing here is hand-labeled from a blank page — you're
always correcting the engine's own guess, never writing coordinates from scratch.

---

## 1. Prerequisites

Install these first, in order. No GPU is needed anywhere in this project.

1. **Git** — https://git-scm.com/downloads
2. **Java 17 (JDK, not just JRE)** — https://adoptium.net/temurin/releases/?version=17 (pick the
   Windows x64 `.msi` installer). Confirm it worked:
   ```powershell
   java -version
   ```
   should print something starting with `17.`.
3. **Python 3.10 or newer** — https://www.python.org/downloads/. During install, check the box
   "Add python.exe to PATH". Confirm:
   ```powershell
   python --version
   ```

You do **not** need to install Gradle separately — the repo has `gradlew.bat`, which downloads
the correct Gradle version automatically the first time you run it.

---

## 2. Clone the repo and do a first build

Open PowerShell and run:

```powershell
git clone <repo-url> documentUnderstandingEngine
cd documentUnderstandingEngine
.\gradlew.bat test
```

The first run will take a few minutes (downloading Gradle + dependencies). At the end you should
see:

```
BUILD SUCCESSFUL
```

If you see `BUILD FAILED`, stop here and ask for help before continuing — everything below
assumes this baseline passes.

Now set up the Python side:

```powershell
cd ml
python -m venv venv
.\venv\Scripts\Activate.ps1
pip install -r requirements.txt
cd ..
```

(`venv` keeps this project's Python packages separate from anything else on your machine —
you'll need to run `.\ml\venv\Scripts\Activate.ps1` again in any new terminal before running
Python commands from this folder.)

## 3. Repo layout — where things live

```
documentUnderstandingEngine/
├── src/main/java/...                    the engine itself (Java) — you shouldn't need to
│                                          touch this to add training data
├── src/test/resources/gold/             every sample form lives here
│   ├── tools/                            small Python helper scripts (see step 5)
│   ├── cl01/                             one sample = one folder
│   │   ├── source.pdf                    the input PDF

```

## 4. Add a new sample PDF

Pick a real, blank (unfilled) PDF form. Give it a short lowercase-hyphenated name, e.g.
`intake-form-v2`. Create its folder and drop the PDF in:

```powershell
mkdir src\test\resources\gold\intake-form-v2
copy C:\path\to\your\form.pdf src\test\resources\gold\intake-form-v2\source.pdf
```

The file **must** be named exactly `source.pdf` inside that folder.

---

## 5. Run the engine on it

```powershell
.\gradlew.bat run --args="src\test\resources\gold\intake-form-v2\source.pdf"
```

Wait for `BUILD SUCCESSFUL`. This writes several files into `build\detected-fields\`, all named
with a `source-` prefix (this prefix is always `source-` regardless of your sample's folder
name, because the input file is always called `source.pdf`):

- `source-debug.json` — every candidate field the engine found, plus its best attempt at
  assembling them into real fields
- `source-page-N.png` — a rendered image of each page
- `source-annotated.pdf` — the PDF with detected boxes drawn on it

---

## 6. Turn the engine's guess into a reviewable draft

Two commands. First, pull the engine's "best attempt" fields out of the debug json:

```powershell
python src\test\resources\gold\tools\extract_resolved.py build\detected-fields\source-debug.json build\detected-fields\intake-form-v2-resolved.json
```

Then turn that into a draft + review images:

```powershell
python src\test\resources\gold\tools\draft_from_resolved.py build\detected-fields\intake-form-v2-resolved.json src\test\resources\gold\intake-form-v2
```

This writes two things into `src\test\resources\gold\intake-form-v2\`:
- `expected-draft.json` — the engine's guess, reshaped into the gold schema
- `review-page-0.png`, `review-page-1.png`, ... — **one image per page, with colored boxes
  drawn on top of the actual form** so you can see exactly what the engine thinks it found

---

## 7. Review and correct — THIS IS THE STEP THAT MATTERS MOST

Open every `review-page-N.png` for your sample and look at it carefully next to the real PDF.
The box colors mean:

| Color | Means |
|---|---|
| Blue | a label/caption box |
| Green | a value box (where an answer should go) |
| Orange | a checkbox/option box |
| Purple | a table/grid box |

For every box on the image, ask:
- **Is a box missing?** (some real field on the form has no box at all)
- **Is a box in the wrong place?** (too big, too small, covering the wrong text, or offset)
- **Is a box labeled wrong?** (e.g. it says "Client Name" but it's really pointing at "Date")
- **Is there an extra box that shouldn't exist?** (the engine invented a field that isn't real)

Open `expected-draft.json` in a text editor side-by-side with the review PNGs. **Do not
re-type coordinates by hand and do not write a new JSON from scratch.** Every box the engine
got right, leave exactly as-is — just delete or correct the specific fields that are wrong.
Coordinates are `[x0, y0, x1, y1]` in PDF points with the origin at the **bottom-left** of the
page (y increases upward — this trips people up, since it's the opposite of screen/image
coordinates where y increases downward).

If you need to fix a box's position, the fastest way is: zoom into the review PNG, estimate
roughly how far off it is in points (the PDF is rendered at a known scale — check the `SCALE`
constant at the top of `draft_from_resolved.py`, currently `2.0`, meaning 1 PDF point = 2 image
pixels), nudge the number in `expected-draft.json`, save, then re-render just that draft to check
your fix visually before moving on:

```powershell
python src\test\resources\gold\tools\render_review.py src\test\resources\gold\intake-form-v2 expected-draft.json
```

(the second argument tells it to render the still-unpromoted draft instead of a real
`expected.json`). Iterate — don't try to get every coordinate perfect on the first guess.

When every box on every page is correct:
1. Delete the `"_draft": "..."` key from the JSON (it's a marker saying "not reviewed yet" — its
   presence is literally what tells every tool in this repo, including the training pipeline,
   to ignore the file)
2. Rename the file from `expected-draft.json` to `expected.json`

```powershell
# after manually editing and confirming the JSON is correct:
Remove-Item src\test\resources\gold\intake-form-v2\expected-draft.json -ErrorAction SilentlyContinue
# (only if you saved corrections to a new file — otherwise just rename in place)
Rename-Item src\test\resources\gold\intake-form-v2\expected-draft.json expected.json
```

**Only files named exactly `expected.json` (never `expected-draft.json`) count as training
data or get scored by the test suite.** This is the single most important rule in this repo —
an unreviewed draft is the engine's own guess, and training on it would just teach the model to
repeat today's mistakes instead of correcting them.

Finally, confirm your new gold sample doesn't break anything:

```powershell
.\gradlew.bat test
```

This must still say `BUILD SUCCESSFUL` (it re-checks every sample under `gold/`, including
yours, against fixed accuracy floors).

---

## 8. Save the engine output for training

The Python training scripts need a permanent copy of `source-debug.json`, named per sample
(the `build\` folder gets overwritten every time you re-run the engine, so this file must be
copied out before you run the engine on a different sample):

```powershell
copy build\detected-fields\source-debug.json ml\data\raw\intake-form-v2-debug.json
```

---

## 9. Extract training data

```powershell
cd ml
.\venv\Scripts\Activate.ps1
python extract_training_data.py
```

This scans every folder under `gold\` that has a real `expected.json`, matches it against the
saved `<sample>-debug.json`, and writes `ml\data\training_candidates.csv` — one row per
candidate the engine found, with a `matched_gold` column (1 = this candidate corresponds to a
real field you confirmed, 0 = it was noise). Read the docstring at the top of
`extract_training_data.py` if you want the full detail on how that label is computed.

---

## 10. Train the model

```powershell
python train_model.py
```

This prints precision/recall for the model and saves it to `ml\models\`. **Read the printed
warning carefully** — with only one or two reviewed samples, the accuracy number it prints is
not a trustworthy estimate of real-world performance (it's explained in the script's own output
and in its docstring). The more samples you review into real `expected.json` files, the more
meaningful this number becomes. Don't be alarmed by a low or unstable score early on — that's
expected and is *why* we need more samples, not a sign anything is broken.

---

## 11. Repeat

Steps 4–10 are the whole loop. Every new form you add and review makes the model (eventually)
better. There is no shortcut around step 7 (review) — it's the only place ground truth enters
this system.

---

## Troubleshooting

- **`gradlew.bat` fails on first run with a network error** — it needs internet access the first
  time to download Gradle itself and dependencies. Retry.
- **`python` isn't recognized** — Python wasn't added to PATH during install; re-run the
  installer and check that box, or use the full path to `python.exe`.
- **`BUILD SUCCESSFUL` but `.\gradlew.bat test` fails afterward** — read the failure message; it
  usually names which gold sample regressed and by how much, with a detailed report written to
  `build\reports\gold-eval\<sample>.txt`.
- **The review PNG looks totally wrong (boxes way off the page)** — double-check `source.pdf`
  isn't corrupted and actually opens normally in a PDF viewer first.
- **`extract_training_data.py` says "skip \<sample\>: no debug json"** — you skipped step 8
  (copying `source-debug.json` into `ml\data\raw\`) for that sample.
